FLOW

Forward-deployed Local Operations Workspace

Several AI coding agents, one governed lifecycle, and not a single boundary crossed without you saying so.

FLOW is a local console and controller for running real delivery work through Claude Code, Codex, Gemini and Microsoft Copilot. It keeps the plan, the roles, the approvals and the evidence in one auditable record on your own machine — and it refuses, loudly, when something tries to skip a step.

runs on 127.0.0.1 your credentials never leave the machine no agent self-authorises

github.com/poornimaka99x/fde-local-workspace

The only three things you ever have to type
APPROVE PLAN <run-id>

Confirms the plan and the role assignment together. Until this, nothing has been read — not Jira, not your client context, not a repository.

APPROVE CODEX <run-id>

One write, 30 minutes, bound to the SHA-256 of one task file. Edit the task and the approval is refused rather than stretched.

APPROVE PUBLISH <run-id>

One target at a time. Approving Jira says nothing about Confluence, Figma, GitHub or a deployment.

Holding a role authorises nothing. A plan existing is not a reason to create anything.

The idea

Two sentences that explain the whole system

Identities are not roles.
Claude: work, Claude: bedrock, ChatGPT/Codex, Gemini and Microsoft Copilot are who is in the room. Who researches, who architects, who reviews and who implements is decided by you, at the start of every run, and is never inherited from the last one. Any identity may hold any role it is capable of; one identity may hold several; none is a valid answer.
Nothing crosses a boundary without you.
Nothing is read until you approve the combined plan and role assignment. Codex writes only under a one-time approval bound to the exact bytes of one task file. Anything that leaves the machine — Jira, Confluence, SharePoint, GitHub, Bitbucket, Figma, a deployment, an email — needs its own publication approval.
A refusal is the product working.
FLOW would rather stop than guess. roles are not confirmed, task file changed since approval, not in this run's plan — each refusal names the missing thing and the exact command that supplies it. There is no --yolo and no danger-full-access anywhere in the toolkit, and fde doctor fails if one ever appears.
Progress is a claim, not a file listing.
State comes from the controller, never inferred from which files happen to exist. A present artifact is not a finished stage. Every run carries an append-only event log and an approval ledger under ~/.claude-shared/runs/<run-id>/.

Service connections. These never become role identities, and configuring one never authorises an external write. Tokens are written to ~/.claude-shared/secrets/service-connections/ with owner-only permissions — which also avoids an interactive Keychain prompt — and the browser never gets them back.

Two Atlassian entries, on purpose

The REST connection is an email and API token FLOW holds, and powers the bounded link reader. Rovo is client-owned OAuth over MCP. They are different credentials with different owners, so they are configured separately rather than pretended to be one.

Figma is wired late

Figma uses the official remote MCP endpoint and its OAuth credential stays owned by the MCP client. It is connected only after roles are confirmed, and canvas writes still need fde approve-publish <run-id> figma.

Git stays the way you touch code

Bitbucket and GitHub connections are for work items and pull requests. Local git remains the primary interface to repositories — the connector is not a substitute for it.

MCP servers. Credentials are stored owner-only and injected into one child process; nothing on that page ever shows a stored value. Versions are pinned, nothing installs itself, and neither npx nor uvx runs because you opened a page.

Switches apply to new processes

Turning a capability off changes what the next FLOW process loads. Sessions already running keep the capability set they started with, so nothing is pulled out from under a live run.

Each switch uses the real mechanism

MCP changes go through the governed MCP controller, disabled tools become explicit CLI deny rules, and hook changes rewrite the local plugin manifest. Nothing relies on asking an agent nicely.

Extensions stay local

You can author a skill into the separately managed fde-user plugin, or import a local plugin containing .claude-plugin/plugin.json. Imports are copied in, bounded in size, and reject symbolic links; they never overwrite an existing plugin.

The workspace

Four ways in — and only two of them are governed runs

Not every question deserves a twelve-stage lifecycle, and not every lifecycle should be assembled from scratch. FLOW keeps the governed path, the pre-configured path and the ungoverned path visibly separate, so you always know which one you are on.

1 · The FDE lifecycle — a governed system you configure once

A normal run is scoped by conversation every time. A system is the opposite: a named, versioned execution profile you set up once and start repeatedly. Forward Deployed Engineer ships as the first one — the complete, independently reviewed delivery lifecycle, tracked separately from ad-hoc runs and with its own run history.

Versioned configurations

Each configuration is named and versioned. Turn stages off, choose the default orchestrator, and point it at the capability catalogue for skill, sub-agent, MCP, tool, plugin and hook control. Create as many as you have kinds of engagement.

A shorter way in

The start wizard asks for four things — configuration, project, orchestrator and the business intent — instead of scoping from a blank sentence. Everything downstream is the ordinary lifecycle.

Same gates, no exceptions

A system changes how a run is assembled, never what it is allowed to do. Role selection, APPROVE PLAN, the Codex write binding and publication approvals all survive intact.

2 · Projects — the folder runs belong to

A project is a name, a description and a list of repository paths. That is deliberately all it is: it holds no workflow state, so grouping runs can never change what any of them is permitted to do.

Repositories must already exist

FLOW never clones, initialises or modifies a repository to satisfy a project. Point it at a directory that is already on disk, or it refuses.

Nothing is orphaned

Runs created before projects existed keep working and are listed as unassigned. A project is never required.

Deleting is conservative

Deleting a project moves only its metadata to trash, leaves every repository untouched, and is refused outright while any live chat or run still refers to it.

3 · Chats — thinking out loud, with nothing switched on

Sometimes you just want to ask something. A chat creates no run, no roles, no plan, no approvals and no checkpoints. It starts in restricted plan mode with permission prompts denied, and its tools are off until you deliberately turn one on — so the safe path is also the default one.

A chat has no plan, roles or approvals behind it, so a connection is offered only where the tool scope can actually be enforced.

Links, not credentials

A granted REST connection resolves only the Jira, Confluence, GitHub or Bitbucket links that appear in your message. FLOW hands the chat the result — the token never reaches the AI CLI or the chat record.

Offered only where it can be enforced

Codex chats get an explicit allowlist of read-only tools in a read-only sandbox. Claude chats get a connection only when every tool it offers reads. Gemini chats get none — its CLI cannot load per-chat MCP config, and FLOW will not widen the machine-global setting to fake it.

Its own storage and its own bin

Chats live under ~/.claude-shared/chats, quite separate from runs. Deleting one moves its record to .trash and never touches the files you attached.

4 · Sessions — several runs open at once

Real delivery work does not happen one run at a time. Each Claude-led run gets its own orchestrator session — exactly one fde-start --resume <run-id> process, one per run, never two — running in an embedded terminal and streamed to its Session tab. You switch between them from the sidebar; they keep running while you are looking at something else.

The sidebar is the switcher

A Running group pins every live session with a live badge; Recents holds what you touched last, with its age. Click one and you are back in that conversation exactly where it was — the session was never paused.

Choices survive a resume

The model and effort you picked at creation are written into the run manifest and reapplied by fde-start on every resume, so a run does not quietly change model between sittings.

Stopping ≠ deleting

Deleting a finished session only forgets its terminal scrollback — the run itself is untouched. Deleting the run is controller-owned, moves the whole directory to runs/.trash, and is refused while its terminal or a design-panel worker is still alive.

A Codex-led run is labelled honestly instead of faked. The console can only hold a fde-start conversation for Claude profiles, so a run driven from Codex says so rather than offering a Resume button that would not work. You drive that one from its own Codex task.

A run, end to end

Four questions, then it gets to work

You don't drive FLOW with controller commands. You start the launcher, choose the Claude identity that will orchestrate, describe the request in a sentence, and make the decisions in chat. It runs the fde calls behind each answer and holds the record. 

# start the orchestrator conversation
fde-start                              # choose work, msc, alt or bedrock
fde-start --orchestrator bedrock       # or select it directly

1 · Is this the ask?

It reads your sentence back before acting on it. A Jira key at the start is picked up automatically.

2 · Is this the plan?

It proposes the stages your sentence implies and shows what it is not doing. Most work is a slice, not the full lifecycle.

3 · Who should do each job?

It shows the required specialist roles, why each is needed, and every eligible identity. Accounts have no fixed roles.

4 · Do you approve all of it?

One summary of request, plan, deliverables, assignments, access and remaining hard gates. Then you type the phrase.

Nothing has been read at this point. Not Jira, not your client file, nothing. The Atlassian connector is in nobody's global config, so it cannot be used during scoping — it appears only after the combined approval. That is why the session then hands you over: the orchestrator asks you to type /exit once, and fde-start resumes the same conversation with the run-scoped connectors enabled.

The twelve stages, and the gates between them

A run is a slice of the pipeline, not all of it. The plan decides which stages this run does, and everything downstream follows it — the role question shrinks to fit, fde status shows only the artifacts in scope, and fde invoke refuses a stage that is not in the plan. Design panel

Three accounts, identical context, one argument worth having

Ask one model to design a screen and you get one answer with no way to tell how contingent it was. A design panel gives two or three separately authenticated Claude accounts the same sealed bytes, keeps them from seeing each other, and reconciles what comes back into one recommendation that records what it rejected and why.

It is a normal run in a named shape — not a second orchestration system, and not three unrelated chats. What is new is that uiUxDesign may be held by several identities at once.

intake→ solution architecture→ adversarial review→ reconciliation→ presentation

The panel works in the two highlighted stages. Everything else is the ordinary lifecycle.

The sealed context is the whole point

Every participant's prompt is the shared bytes, then its own lens block — and the shared context is a strict prefix of every prompt. The controller asserts it and the test suite proves it. That is what makes “everyone got the same context” checkable rather than merely intended.

It is built once, written to artifacts/design-panel/common-context.md, and reused byte-for-byte. context-manifest.json records exactly what went into it — so months later you can answer what the designers were actually looking at.

Images are sealed by bytes, not by path

A selected image is copied into media/ and that copy is what participants get. It is re-hashed at every start, so an image that changed between two participants refuses the second start rather than quietly giving two accounts different bytes under one context digest.

The selection is bounded and explicit

No repository is traversed and no folder is inlined. At most 12 attachments, 256 KiB each, 64 KiB inlined each, 512 KiB of context in total. Guidance is cut on whole section boundaries and the manifest records how many bytes of each document were used.

Refused before it starts, not after

Symlinks, sensitive paths, and an attachment whose bytes no longer match its digest are all refused. A file that is not UTF-8 text and is not an image type the installed CLI can accept is refused before the panel runs, rather than turned into prompt text.

Independent-first, or a staged handoff

Independent-first — the default

No participant sees another's proposal until every one of them has finished or failed, and the controller refuses a prompt that contains one. You get genuinely independent reads of the same brief.

Collaborative — order enforced

Participants work in their configured order. Each one receives the succeeded proposals ahead of it in a <handoff> block carrying each proposal's digest, and is told to say what it adopts, changes and rejects. A failed predecessor hands nothing on and does not block.

In collaborative mode an earlier participant cannot be retried once a later one has worked — that would replace a proposal somebody was already given. Start a new run instead. Every handoff writes a design-panel.handoff event naming who received which proposals by digest.

What a participant is allowed to do: nothing

No tools at all

Each runs with --tools '', --restricted, --strict-mcp-config and plan-only permissions, so it cannot write a repository even if something in its context told it to. Concept generation writes nothing but the run.

Its own credentials, always

Every participant runs under its own CLAUDE_CONFIG_DIR. No profile's environment is merged with another's — the isolation guarantee is a real Claude-profile one, not a convention.

Real ceilings, real Stop

A wall-clock ceiling (15 minutes by default), an output ceiling, at most three running at once, and a Stop that actually kills the process.

Three output targets

recommendation

A document: the comparison, the reconciliation, and the final design recommendation.

design-to-code

The same, plus a handoff section on the reconciliation for whoever implements it.

prototype

An artifact, not a description of one. Each proposal must carry a ## Prototype section holding exactly one fenced HTML block — a complete, self-contained document with nothing fetched over the network.

For a prototype the controller refuses a proposal that describes a prototype instead of delivering one: nothing is recorded, and the participant stays running and retryable. Extracted files land in artifacts/design-panel/prototypes/ and the console previews them with scripts off.

Reconciliation, and the approval that stops a walkover

Reconciliation runs in the reconciliation stage under the run's orchestrator account and needs two successful proposals. With one, it refuses — unless you say otherwise, out loud: 

fde design-panel approve-degraded <run-id>
APPROVE DEGRADED RECONCILIATION <run-id>
That is a typed approval on purpose. A recommendation nothing argued with is a decision, not a default — and the final design says so.

The answer must arrive in exactly these sections, or it is refused and nothing is written. The comparison covers user flow, hierarchy, visual language, components, accessibility, responsive behaviour, motion, risks and implementation cost; the reconciliation lists accepted and rejected ideas explicitly, attributed, with reasons.

Guidance packs, and what wins when they disagree

Optional, off by default, and shown with what each one changes. Taste is visual-direction guidance with three dials — variance, motion and density, each 1–10 and recorded in the panel manifest. Impeccable shapes during concept generation, critiques during review and polishes only after reconciliation; it is a guidance layer only, with no launcher, engine binary or hooks. Design-language references are a catalog of reviewed DESIGN.md documents — at most one primary and one secondary, copied into the sealed context and hashed.

Taste and Impeccable give conflicting stylistic direction. Enabling both is possible, but only after the conflict has been shown to you and you have chosen. And a design-language reference is inspiration for an original, project-specific direction — never authorisation to impersonate a brand or reuse its assets.

When guidance disagrees, this precedence decides — and it is written into every sealed context, so it travels with the work:

#What wins

Starting one

From the console it is two steps, because a panel has two moments: create the run (project, design brief, orchestrator), then seal the context and configure the panel (attachments, participants, lenses, model and effort per account, output target, optional reference and guidance packs, independent-first or collaborative). Between those two steps you can attach files. After the second, the context is sealed — the only way to change it is a new panel on a new run.

Creating the panel proposes the plan and selects the designers. It approves nothing. The panel page then tells you which roles the plan still needs and the exact phrase to type. 
fde start --json --orchestrator work --project <project-id> --shape design-panel -- "Rework returns"

fde design-panel create <run-id> --brief-file brief.md --propose-plan \
    --participant work:flow \
    --participant msc:visual:high \
    --participant alt:system

fde roles <run-id> --set solutioning=work --set review=msc --set presentation=work
fde approve-plan <run-id>              # type: APPROVE PLAN <run-id>
fde resume <run-id> --next             # into solutioning
fde design-panel start <run-id> claude_work --print-prompt

--participant is <agent>:<lens>[:<effort>[:<model>]]. The model is last so a provider model id containing a colon still parses.

When something goes wrong

Orphaned work becomes a retryable interruption the first time the panel is read after a restart. Nothing is silently resumed, and no proposal is lost: what was recorded stays recorded.

What happenedWhat you seeWhat to do
The console restarted mid-runparticipants become interrupted with a reasonRetry them
An account hit a usage limitthat participant is failed, the others untouchedRetry it later, or reconcile with the rest
Only one proposal succeededreconciliation refusesRetry, or approve a degraded reconciliation

A vendored source no longer matches its lockthe panel refuses to use itdesign-sources audit, then update

Limitations, stated plainly

These are in the repository's own documentation, not extracted from it by anyone else. A feature that lists what it is not is usually the one worth trusting.

Claude accounts only
Codex, Gemini and Copilot are not participants. The point is separately authenticated Claude accounts reading identical context, and the isolation guarantee is a Claude-profile one.
Collaborative is not a conversation
It is a staged handoff. There is no shared session, and a participant sees a predecessor's finished proposal, not its reasoning. The accounts never talk to each other live.
Participants have no tools
They cannot read the repository themselves; they see what you sealed into the context and nothing else. That is the trade for the guarantee that concept generation writes nothing.
A prototype is not a build
One self-contained HTML file with no network access — a design artifact to look at and click through. It authorises no repository write.
The reconciliation is one model call
With a required shape. It is evidence and a recommendation, not an approval: implementation, publication and deployment keep their own gates.
The console must be running
The console runs the accounts; the controller owns the record. If the console is not running, nothing progresses — and nothing is lost.

The approvals

Two places you type rather than talk — and that is the point

The approval strings are not something an agent can hear you say by accident. Each one is shown to you with exactly what it authorises before you type it.

Letting Codex write code

Giving Codex the implementation role authorises nothing on its own. The write is a separate, deliberate step. 

fde approve-codex <run-id> implementation \
  --task-file ~/.claude-shared/runs/<run-id>/artifacts/implementation/implementation-task.md \
  --repo ~/work/client-returns \
  --commands "pytest -q"

# you are shown: the repo, the branch, the writable root, the SHA-256 of the
# task file, whether network was asked for, and what it may run. Read it, then type:
APPROVE CODEX <run-id>

fde invoke <run-id> chatgpt_codex \
  ~/.claude-shared/runs/<run-id>/artifacts/implementation/implementation-task.md --write
One use, 30 minutes, bound to those exact bytes. Codex runs non-interactively with --sandbox workspace-write: the filesystem is bounded to the approved root and network is off. Edit the task file and the approval is refused rather than stretched — approve the new one.

Letting anything leave the machine

fde approve-publish <run-id> jira --summary "8 stories under ACME-142"
APPROVE PUBLISH <run-id>

confluence create ENG "ADR 004: Token exchange" \
  ~/.claude-shared/runs/<run-id>/artifacts/architecture/adr.md --parent 123456

One target, one approval. jira-plan.json is a preview — a plan existing is not a reason to create anything. Figma canvas writes take the same route: fde approve-publish <run-id> figma.

Output hygiene runs before anything is published

Every legal transition into publication or complete applies a narrow, provenance-preserving hygiene policy to files under artifacts/ and writes a hashed JSON report under artifacts/evidence/.

It removes

Unsafe invisible Unicode, local home-directory prefixes, and selected personal or path-like Office properties.

It preserves

Creator, copyright and ownership fields, visible watermarks, C2PA content credentials, symlinks and unknown binary metadata.

Preview it at any time with fde output-hygiene <run-id> --check.

Governance

Read-only is enforced, or it is not claimed

A prompt is not a control. Each client gets its scope in its own mechanism — Claude permission rules with exact tool names and no wildcards, Codex enabled_tools, Gemini includeTools — built from the tool list the server actually reported.

StateWhat it means
catalogueFLOW knows how to run this server. That is all it means.
configuredYou supplied the settings and credentials it declares.
readyAlso installed, and a bounded verification succeeded.
activeIn a specific run's or chat's effective set, because that run's approved stages, roles and profile call for it.

Where a provider offers no verifiable read-only subset, the server stays inactive and reports blocked with the reason instead of being described as safe. Atlassian and Figma are the honest exception — their OAuth token belongs to the MCP client, so FLOW cannot enumerate their tools, and every surface says so. fde mcp effective --run <id> shows what one run may actually reach, and why anything else may not.

Ten servers, pinned

Context7 and Serena for code, Playwright and Chrome DevTools for the browser, Atlassian and Figma for delivery and design, DBHub, AWS, Azure and Langfuse for data, cloud and observability.

Profiles narrow, never widen

coding, frontend-testing, client-delivery, data, observability each name a slice of the catalogue for a kind of work.

No permanent privilege

Atlassian is role-scoped: it stays out of every global config and is written per run, for whichever identity holds the role. There is no permanently privileged orchestrator account, because there is no permanent orchestrator.

Four layers, so nothing leaks between engagements

LayerLives inChanges when
Shared — how you work, standards, client context~/.claude-shared/rarely
Toolkit — skills, agents, commands, MCP servers, hooks~/.claude-shared/fde-toolkit/when you build a capability
Run — one requirement, its roles, approvals, artifacts~/.claude-shared/runs/<run-id>/constantly, and never shared
Repo — what this codebase is<repo>/CLAUDE.md + <repo>/.claude/per engagement

Plus one config directory per identity in ~/.claude-profiles/, holding only auth and provider settings. The shared layer is symlinked into each, so every profile sees the same context without duplicating it — and one account's settings never leak into another's.

One instruction file, three agents

The other CLIs disagree about which instruction file to read and each stores MCP config in a different place and shape. FLOW makes AGENTS.md the single source and generates the adapters.

ToolReads AGENTS.mdAdapter
Codex CLInativelynone
Claude CodenoCLAUDE.md containing @AGENTS.md
Gemini CLInot by defaultone-time context.fileName setting

mcp-sync does the same for MCP: one source file at ~/.claude-shared/mcp/mcp-servers.json becomes a Claude .mcp.json, a Gemini settings.json and a Codex config.toml. Servers FLOW manages are tagged _fdeManaged, so a server you added by hand survives an update.

GitHub Copilot is not part of this ecosystem. ask-copilot is a stub that says so, mcp-sync never reads or writes ~/.copilot, and your existing configuration there is left alone. “Copilot” here always means Microsoft 365 Copilot / Copilot Studio.

Get started

About thirty minutes to a first completed run

Everything below is copy-paste. You need Node 22+ and Claude Code signed in at least once. Codex and Gemini are optional until you actually assign them a role.

Install

Clone the repository somewhere permanent, then look before you write. --dry-run writes nothing.

git clone https://github.com/poornimaka99x/fde-local-workspace.git
cd fde-local-workspace

./install.sh --update --dry-run     # look first — nothing is written
./install.sh --update
exec $SHELL -l

This creates the profiles work, msc, alt and bedrock — or name your own with ./install.sh work bedrock. The installer never deletes, shows you a diff before replacing anything you customised, and backs up what it replaces into ~/.claude-shared/.backups/. Your client contexts, intake files, run history, logins and profile settings are never touched.

Create your credential file by hand

The installer deliberately does not copy any .env.sh out of the repository: a secret should never travel with the source, and never into a cloud-synced folder. Your shell sources ~/.claude-shared/env.sh, which you create once, from the template. 

cp claude-shared/env.sh.example ~/.claude-shared/env.sh
chmod 600 ~/.claude-shared/env.sh
open -e ~/.claude-shared/env.sh    # CONFLUENCE_BASE_URL, EMAIL, API_TOKEN
source ~/.claude-shared/env.sh

confluence spaces                  # should list your spaces

Get an Atlassian API token at id.atlassian.com → Security → API tokens. Set CONFLUENCE_BASE_URL to your own site and CONFLUENCE_EMAIL to the account that token belongs to. This file is gitignored, is never read into an agent prompt, and fde doctor warns you if its permissions are looser than 600.

Check what you have

fde doctor

Read it as three groups:

MarkerMeaning
BROKEN*Blocks you. Fix before going further.
--Advisory. Codex and Gemini missing is fine if you are not assigning them roles yet; Copilot Studio unconfigured is fine — it needs your admin.
okDone.

Want the two extra CLIs?

npm i -g @openai/codex @google/gemini-cli

Sign in once per identity

cc-work   cc-msc   cc-alt      # personal accounts
cc-bedrock                      # an org account on AWS Bedrock
cc-which                        # what exists, what's active

Bedrock account settings live in the FLOW account registry — choose the AWS profile and region when adding the account, or change them later under Configuration → AI accounts. FLOW exports those values for verification and every launch.

Open the console

cd fde-gui
npm install        # once
npm start          # builds the UI, serves it on 127.0.0.1:7317

Open the link the server prints — it looks like http://127.0.0.1:7317/#token=…. The token lives in the URL fragment, which the browser never sends to a server, so it stays out of logs and history sync. It is valid for that launch only; a tab opened without it is refused.

Your first run

You do not drive this with controller commands. Start the launcher, choose the Claude identity, give it the request in a sentence, and answer the four questions in plain English. 

fde-start                       # choose work, msc, alt or bedrock

When it shows you one combined summary of the request, plan, deliverables, assignments, access and remaining hard gates — and only when it is correct — type the exact phrase it gives you: 

APPROVE PLAN <run-id>

Then type /exit when prompted. fde-start resumes the same conversation with the run-scoped connectors enabled, and works the stages you agreed to. Within clear approved scope it uses its normal configured tools without asking for each routine operation; it stops and asks when intent, target, authority, destructive effect, acceptance criteria or required evidence is ambiguous.

Watch it from outside

Ask in the session — “where is this?”, “what's next?”, “park it, I need to check with the PO” — and it runs the right command. The CLI is there for when you want to look from another terminal. 

fde status <run-id>    # plan, roles, artifacts, approvals, next step
fde list               # all runs
fde shapes             # the named plan shapes

Still needs someone else

Copilot Studio

Needs a licence and a published agent. The Direct Line secret goes in the Keychain, not env.sh:
security add-generic-password -a "$USER" -s fde-copilot-directline -w

Bitbucket via Atlassian

Depends on token scopes and whether the site is linked to your organisation. Ask your admin. Local git works regardless, and is still the right way to touch repositories.

Client context

Run /client-context <slug> before real work. It is why agent output either sounds like your client, or sounds like nobody.

Checking it still works

python3 -m unittest discover -s tests
fde doctor

The controller and harness suites run against temporary homes and a stub Codex; they never touch your real configuration.
